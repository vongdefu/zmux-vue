# 架构选型与实现方案分析

> 背景：本项目（zmux-codex / ZMusic）已趋于完善，实际使用中存在三个问题：
>
> 1. 使用终端多为手机；
> 2. 数据保存在本地，无法多端同步；
> 3. 可能需要多用户使用，且部分功能收费。

---

## 一、核心判断：后端是「必选项」，不是「选项之一」

把三个问题翻译成技术需求，会发现它们指向同一个结论：

| 你的问题               | 技术需求                            | 结论             |
| ---------------------- | ----------------------------------- | ---------------- |
| 手机为主               | 移动端可用（响应式 / 小程序 / App） | 客户端形态问题   |
| 数据本地、无法多端同步 | 数据上云，本地只做缓存              | **必须有服务端** |
| 多用户 + 部分功能收费  | 账号体系 + 支付 + 权益校验          | **必须有服务端** |

**同步、多用户、收费三者都要求一个后端。** 所以「BS 架构」不是三个并列选项之一，而是绕不开的底座。真正要决策的是两件事：

1. **客户端形态**：纯 Web（H5/PWA）、微信小程序、原生 App、跨端 App——选哪个或哪几个；
2. **后端形态**：自建服务器、BaaS（Supabase/Firebase/LeanCloud）、微信云开发。

而「浏览器插件」可以直接排除（见下）。

---

## 二、方案二「浏览器插件」——排除

| 维度     | 结论                                                                                    |
| -------- | --------------------------------------------------------------------------------------- |
| 形态本质 | 插件是「增强浏览器」的（广告拦截、页面增强），不是承载一个音乐/日程/习惯/记账的完整 App |
| 移动端   | **完全不可用**——插件只在桌面 Chrome/Firefox/Edge 运行，和「手机为主」直接冲突           |
| 分发     | Chrome Web Store / Edge Add-ons / AMO，审核和付费能力都很弱                             |
| 付费     | 插件内支付生态极不成熟，收费困难                                                        |

**结论：直接放弃。** 它和核心诉求背道而驰。

---

## 三、方案一「App」—— 四条子路径，成本和体验差异巨大

| 子路径                         | 复用现有 Vue 代码                          | 移动体验               | 分发                     | 收费抽成                         | 开发成本   |
| ------------------------------ | ------------------------------------------ | ---------------------- | ------------------------ | -------------------------------- | ---------- |
| 原生（Swift + Kotlin）         | 零复用，两套代码                           | 最好                   | App Store / 应用宝等     | iOS 数字内容强制走 IAP（15–30%） | 最高，翻倍 |
| 跨端（Flutter / React Native） | 逻辑可参考，UI 重写                        | 好                     | 同上                     | 同上                             | 高         |
| **跨端 Vue（uni-app / Taro）** | **高复用**（Vue 语法、组件逻辑大部分可搬） | 好                     | 小程序 + H5 + App 一套出 | 小程序/App 各有规则              | 中         |
| Hybrid 壳（Capacitor）         | 极高复用（直接包现有 Web）                 | 中（WebView 性能略降） | App Store / APK          | 同上                             | 低         |
| PWA                            | 极高复用（就是现有 Web）                   | 中（iOS 受限）         | 免商店，加到主屏         | 自建支付，无抽成                 | 最低       |

关键点：

- 已经有一套成熟的 Vue 3 代码，**原生 App 意味着全部重写，最不划算**。
- 如果走 App，最自然的是 **uni-app/Taro**（Vue 系跨端，一份代码出小程序 + H5 + App）或 **Capacitor**（直接套壳现有 Web）。
- 但 App 有硬约束：**iOS 上卖数字内容（订阅、解锁功能）必须走苹果内购 IAP，抽 15–30%**，且要有开发者账号（$99/年）和审核。这对「部分功能收费」是个实打实的成本。

## 四、方案三「BS 架构」—— 正解，且是现有代码的自然延伸

当前项目**本质上已经是一个 SPA**（`App.vue` + `currentView` 切换，无路由），只是「前端 + localStorage」。BS 架构不是重写，而是**给现有的壳补一个后端**：

- **前端**：几乎不动。现有的响应式已经把 App 限制在 `max-width: 430px` 的手机壳里，手机浏览器打开就是移动端体验。
- **后端**：新增账号、云存储、同步、支付。
- **数据层**：代码里存储模块已经被干净地隔离了——`libraryStorage.js`、`scheduleStorage.js`、`pomodoroStorage.js`、`habitStorage.js`、`accountingStorage.js`、`calendarStorage.js`。**这些就是天然的「接缝」**：把它们从「写 localStorage」换成「本地缓存 + 服务端读写」，UI 和业务逻辑几乎不用改。

额外红利：现在搜索/下载是前端直连第三方音乐 API（Meting 等）。有了后端，可以**服务端代理 + 缓存**这些请求，反而更利于规避风控、做全用户共享限流。

## 五、关键补充：微信小程序（对「手机为主 + 多用户 + 收费」可能是最优解）

语境（中文、网易云/QQ/酷我音乐源、手机为主）强烈指向中国大陆市场。这种情况下**微信小程序**价值极高，值得单独列出：

| 维度     | 微信小程序                                 |
| -------- | ------------------------------------------ |
| 手机体验 | 接近原生，无需下载安装，即点即用           |
| 账号体系 | **天然带微信身份**，几乎免登录开发         |
| 支付     | **微信支付原生集成**，无商店抽成           |
| 分发     | 微信内传播（分享/搜索），无 App Store 审核 |
| 成本     | 微信云开发可免自建服务器                   |

**uni-app** 恰好是 Vue 语法，能让**一份代码同时出小程序 + H5 + App**——这对现有 Vue 3 代码是最友好的迁移路线。

## 六、具体技术选型建议

### 前端（保持 Vue 生态）

- **继续用现有 Vue 3 代码**做 H5/PWA；若上小程序/App，用 **uni-app**（Vue 语法，一码多端）。
- 移动端补一个 PWA manifest（图标、离线、全屏），手机浏览器即可「添加到主屏幕」。

### 后端（按技术背景和精力选）

| 方案                            | 适用       | 优点                                | 缺点         |
| ------------------------------- | ---------- | ----------------------------------- | ------------ |
| **Supabase**（国际）            | 全球化     | Auth + Postgres + Realtime 开箱即用 | 国内访问不稳 |
| **LeanCloud**（国内）           | 中国大陆   | 国内 BaaS，账号+云存储+推送         | 生态较小     |
| **微信云开发**                  | 小程序     | 云函数+云库+微信支付免服务器        | 绑定微信     |
| **自建 Node（NestJS/Fastify）** | 想完全掌控 | 灵活、可控成本                      | 开发量大     |

对 solo/小团队，**优先 BaaS 或云开发**，把精力省下来做业务，而不是造轮子。

### 数据库 / 认证 / 支付

- **数据**：数据模型是「每模块一个 JSON 键」，非常适合 Postgres 的 `user_id + module + jsonb`，或直接文档型存储，迁移成本极低。
- **认证**：国内用微信登录（小程序天然带 / 公众号 OAuth），国际用邮箱/Google OAuth + JWT。
- **支付**：国内微信支付/支付宝（无抽成）；国际 Stripe（约 2.9% + $0.3）。**注意：只有 iOS 原生 App 卖数字内容才被强制 IAP**，走 Web/小程序/Android 侧载可以绕开 30% 抽成。

### 同步策略

- 推荐「**本地优先（local-first）+ 后台同步**」：localStorage 作为离线缓存，服务端为准，登录后拉取、变更时推送。离线可用、多端一致。
- 或更简单的「服务端为准」，每次操作直接读写 API（弱网体验略差但实现最省事）。

## 八、我的推荐（分阶段，低风险）

> **先不重写，把现有 Web 升级成「带后端的 Web/PWA」，验证付费需求；再按渠道用 uni-app 出小程序/App。**

**阶段 1（1–2 周，验证 MVP）**
保留现有 Vue 前端，接一个后端：把 6 个 `*Storage.js` 从 localStorage 换成「本地缓存 + 服务端同步」，加账号 + 登录 + 简单付费。后端用 Supabase（国际）或 LeanCloud/微信云开发（国内）。部署 Vercel/Netlify 或国内云 Serverless。手机直接浏览器访问 + PWA 加到主屏。

**阶段 2（移动体验打磨）**
PWA 完善（离线、全屏、图标）；若渠道需要，用 **uni-app** 把现有组件迁移，一套代码出 **微信小程序 + H5**。

**阶段 3（按需扩展）**
小程序/App 上架、订阅体系、支付回调、权益校验完整化。

## 九、需要拍板的问题 + 两个重要风险提示

在写任何方案/代码前，这几个答案会决定技术栈，建议先想清楚：

1. **目标市场**：中国大陆为主，还是全球化？——决定微信小程序 vs PWA/Supabase。
2. **团队/精力**：solo 还是有后端开发？——决定 BaaS 还是自建。
3. **收费模式**：订阅制、买断、还是「免费+付费功能」分级？——决定支付和权益模型。
4. **是否需要真正的应用商店分发**（而非小程序/网页）？——决定是否值得承担 IAP 抽成和审核。

### ⚠️ 两个风险，务必重视

1. **版权/合规**：当前音乐源来自第三方 API（网易云/QQ 等）。**商业化一个依赖未授权音乐源的产品，法律风险很高**。服务端千万别存储/分发音频文件本身（只存用户自己的歌单元数据、偏好、日程等），能显著降低风险。
2. **数据合规**：一旦存用户数据上云，国内需考虑《个人信息保护法》（PIPL），需要隐私政策、用户同意、数据删除机制。
